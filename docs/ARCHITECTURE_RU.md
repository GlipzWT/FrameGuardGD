# Архитектура и дальнейшие шаги

## Слои

1. `Planner.hpp`: независимая линейная модель. Нет Geode/Cocos, нет мутаций игры.
2. `Assist`: допустимость, захват физического ввода, ограниченная очередь,
   история PlayerCheckpoint, local rewind, bounded collision grace.
3. Хуки: handleButton, PlayerObject update, PlayLayer lifecycle/death.
4. `Panel`: визуальные настройки и переход в стандартные настройки Geode.

## Почему не вызывается update всего уровня ради каждого прогноза

Повторный вызов GJBaseGameLayer::update изменяет мир: триггеры, звук, статистику,
камеру, активные объекты и очередь команд. Копирование координат игрока назад
не отменяет эти эффекты. Эта альфа сознательно не выдаёт подобную схему за
безопасный simulator. Для планирования используется отдельная модель, а
локальный откат явно ограничен статикой и Practice.

## Порядок ввода

- Событие, которое не удалось проверить, проходит обычным путём.
- Не меняется предсказанно безопасный immediate input.
- Выбирается ближайшая по модулю допустимая коррекция; при равной величине
  предпочитается задержка, а не откат.
- Следующий физический фронт не переносится через предыдущий: история
  очищается на событиях ввода.
- Если отложенный фронт ещё не пришёл, следующий фронт сбрасывает ожидание
  с применением предыдущего фронта перед новым.
- Rollback=false полностью запрещает локальный rewind и grace suppression.

## Известные недостатки реализации

- Точные хитбоксы GD и положение потолка/границ камеры не воспроизводятся.
- Штатный PlayerCheckpoint не является снимком всех компонентов игрока;
  вкупе с аналитическим catch-up возможны остаточные рассинхронизации полей.
- Реальный момент handleButton относительно физического шага надо замерить
  в игре. Без этого нельзя обещать однокадровую точность интеграции.
- Визуальный след сбрасывается после локального отката; возможен скачок.
- Static audit ограничивает весь уровень, даже если опасный триггер далеко.
- State/HUD и режим UI не проходили live QA в Cocos2d.
- На реальной карте помощь может быть почти всегда отключена из-за строгого
  audit или неточности внешней AABB Wave. Это не повод маскировать отказ.

## Чтобы получить полноценный вариант первоначальной идеи

1. Сначала собрать и проверить Windows-интеграцию; добавить реальные трассы
   input/tick/collision и regression fixtures для конкретной версии GD.
2. Точно определить fixed simulation tick и согласовать ввод с CBF/TPS,
   либо жёстко запретить несовместимые комбинации.
3. Заменить приближённый collision oracle изолированной симуляцией с точными
   ориентациями, формами, специальными правилами Wave и границами мира.
4. Ввести snapshot адаптер состояния уровня: игроки, game state, active/dynamic
   objects, trigger manager, очереди команд и отложенные эффекты.
5. Сделать спекулятивную симуляцию без публикации звука/частиц/статистики.
6. Проверять детерминизм: save → simulate → restore → simulate даёт тот же
   игровой результат. Контролировать весь изменяемый state, а не только x/y.
7. Откатывать snapshot и воспроизводить точную записанную цепочку inputs до
   настоящего. При неуспехе восстанавливать исходное состояние без побочных эффектов.
8. Реализовать корректную отложенную смерть для позднего ввода поверх этого
   snapshot/replay, без неконтролируемого прохождения через препятствия.
9. Только после этого расширять поддержку на динамику, dual и другие формы.

Это отдельный существенный этап разработки. В этой версии он не сделан и
не скрыт за красивым переключателем «полный rollback».
